# 10. MCP Git Over Bash Git for Agent Permissions

**Status:** accepted
**Date:** 2026-03-27

## Context

AI agents need git access for status, diff, log, and staging operations. The initial approach used Bash wildcard permissions (`Bash(git status*)`, `Bash(git diff*)`, etc.) in `settings.json`. This worked but had a safety gap: `Bash(git branch*)` matched both `git branch --list` (read-only) and `git branch -D` (destructive deletion). Wildcard patterns cannot distinguish safe from unsafe flag combinations.

Additionally, Bash git permissions allow command chaining (`&&`, `||`, `;`) within a single shell invocation, and return unstructured text that agents must parse.

## Options Considered

1. **MCP git server** — structured tools with typed parameters, one tool per operation, no shell involved
2. **Tighter Bash wildcards** — more specific patterns like `Bash(git branch --list*)` to exclude destructive flags
3. **Custom wrapper scripts** — shell scripts that validate arguments before passing to git

## Decision

Use an MCP git server. Which server (amended 2026-11-22): the toolkit's own, `tools/git-mcp/server.js`, one node file with no dependencies, registered under the same name `git-mcp` with the same tool and parameter names, so no hook, permission rule or agent tool list changed. It replaced the third-party `@cyanheads/git-mcp-server` for two reasons: memory (that server measured 88 MB per session against about 16 MB here, with macOS `footprint` on 2026-11-22, and every session starts its own), and ownership of the code every git write passes through (a 6.9 MB bundle against one file reviewed in this repo). The decision itself stands. Each git operation is a separate tool (`mcp__git-mcp__git_status`, `mcp__git-mcp__git_diff`, etc.) with validated parameters. The setup template auto-approves the read-only tools and the writes an agent needs on its own branch (`git_add`, `git_commit`, `git_branch`, `git_checkout`, `git_fetch`, `git_pull`, `git_merge`, `git_push`, `git_stash`, `git_tag`, `git_cherry_pick`, `git_rebase`, `git_reset`). An allow rule skips only the prompt and the auto mode classifier: the PreToolUse hooks still run, and `hooks/git-mcp-guard.sh` denies a missing or relative repo path on every git tool that takes one, reads included, always denies `git_set_working_dir` and `git_clear_working_dir`, and, on push, force and delete pushes, pushes to `main`, `master` and `production`, and a remote that is not configured in the repo; it also denies hard resets, clean and worktree. It does not cover `git_checkout` discarding uncommitted work, branch and tag deletion, stash drop, or a credential in a file the secret detector never sees (it reads the commit message only). Every other tool (`git_remote`, `git_clone`, `git_init`) still prompts for confirmation, and the working-dir tools are denied; `git_remote` stays off because its `set-url` mode can redirect `origin`.

MCP tools are better for three reasons: granular per-tool permissions (no wildcard ambiguity), structured input (the hooks read named fields, not shell text), and no command chaining risk (no shell involved). The own server answers with git's own text, not JSON fields: nothing in the toolkit parsed the fields. Tighter wildcards would be fragile — every new flag combination needs a new pattern. Wrapper scripts add maintenance burden and still run through the shell.

## Consequences

- Bash git permissions are fully replaced — `setup-claude` migrates old patterns automatically
- The git-mcp server must be registered at user scope (`claude mcp add --scope user git-mcp -- node <checkout>/tools/git-mcp/server.js`); it runs from the checkout, so nothing is installed and a merge plus a pull is the update
- The toolkit owns the server's input validation: a closed parameter set and strict types per tool, no value that git could read as an option, a remote that is a name and never a URL, and no inherited `GIT_*` environment ([tools/git-mcp/README.md](../../tools/git-mcp/README.md)). The hooks decide what is allowed; the server decides what a call can mean, and a change to a parameter's name, default or meaning there changes what the hooks decide
- Agents pass an explicit `path` on every call: the server keeps no working directory and refuses a missing or relative `path` itself (the earlier server had one global working directory, moved by `git_set_working_dir` and shared by every agent); `hooks/git-mcp-guard.sh` still denies a missing or relative `path` on every git tool, and the working-dir and worktree tool names, which the server no longer offers
- Non-git Bash permissions (`ls`, `wc`, `pwd`, `which`, `mkdir`) remain — no MCP equivalent exists; `Bash(cat *)` is removed, since the Read tool covers it
- Bash git has one owner (amended 2026-11-19; before it, `hooks/protected-paths-guard.sh` and `hooks/destructive-blocker.sh` each kept their own reader of Bash git as a backstop). `hooks/git-mcp-redirect.sh` denies every Bash git command except a short allowlist of read-only plumbing with no MCP equivalent (`rev-parse`, `ls-files`, `config --get`, and the like; a subcommand nobody listed is denied), and sends the rest to the matching MCP tool. It reads the command with the shared parser (`hooks/lib/shell-parse.sh`), so it finds git behind wrappers, shell keywords, redirects and `bash -c`/`eval` strings, and it is fail-closed: wired as `/bin/bash -p "$HOME/.claude/hooks/git-mcp-redirect.sh" || exit 2`, it blocks when jq or a lib file is missing. The cost: no second reader backs it, so a gap in the allowlist or the parser is a Bash git write that nothing else denies. That is why it ends with a net: it counts the `git` words in the raw command (a whole token `git` or a path ending in `/git`, case-insensitive; `.git`, `git-notes` and `gitk` are not one) and denies when there are more of them than git commands the parser read, so a shape the parser misreads or a wrapper it does not know is denied as soon as it names git. The price is a deny for git named as plain text (`grep git`, `which git`, `ls ~/git`, a heredoc or a comment that says git), and a residual: a git word the raw text does not show whole (`g''it`, a variable) behind a shape the parser misses passes; the deny reason points to the Grep and Read tools. The allowlist stays short and each entry has a test; a git name built at run time, an alias, a shell function body written without the word git, a dashed git binary, or a script that runs git are the known gaps (the shapes that name git as a word are what the net is for). `git -c` is denied as a guard against mistakes; config set through the environment or a config file and run by `help`, `cat-file` or `describe` is a gap. The setup template allows no Bash git, so a call that slips past still needs a permission prompt or the auto mode classifier, and branch protection on the remote still refuses a push to a protected branch.
- Two hooks enforce the decision: `hooks/git-mcp-redirect.sh` sends a Bash git command to the matching MCP tool, and `hooks/git-mcp-guard.sh` blocks a missing or relative repo path, the working-dir tools, force and delete pushes, pushes to protected branches, pushes to a remote that is not configured in the repo, hard and merge resets, `git_clean` other than a dry run, and worktree operations
- Amended 2026-11-23: the skills `/setup-claude` and `/update-claude` are now `/setup-toolkit` and `/update-toolkit`, with no aliases. The text above keeps the original names.
